# Memory and pattern discovery

Socia uses a layered memory system that separates short-lived conversational context, stored individual observations, and synthesized user-level memories.

## Three tiers

| Tier               | Storage                                                                               | Lifetime              | Used for                                         |
| ------------------ | ------------------------------------------------------------------------------------- | --------------------- | ------------------------------------------------ |
| Working context    | Conversation history plus assembled context (last 10 emotions, active Journey titles) | One request           | Grounding the reply                              |
| Episodic memory    | `episodic_memory` with `vector(768)` embeddings                                       | Persistent            | Similarity retrieval; input to pattern synthesis |
| Synthesized memory | `user_memory` (+ `_evidence`, `_history`)                                             | Persistent, versioned | Stable user context; objects shown as patterns   |

In this production system, a **pattern** is an application-level synthesis of repeated extracted observations. It is **not a statistically validated behavioral pattern or behavioral diagnosis**.

## How a message becomes memory

1. The LLM extracts emotions, behavior observations, and entities as JSON.
2. Items are validated against closed vocabularies and configured ranges (see [architecture](architecture.md)).
3. Each valid emotion or behavior observation becomes an `episodic_memory` row with text in the form `"<tag>: <evidence sentence>"`, together with its `confidence`, `importance` (defaulting to confidence), and an embedding generated by `nomic-embed-text`.
4. Entities are upserted per user (unique on `user_id, name`) and linked to every episodic memory extracted from that message. This graph therefore represents **message-level co-occurrence**, rather than typed relations such as "avoids X".

## Retrieval

Function: `retrieve_relevant_episodic_memories`.

* The incoming message is embedded and the user's episodic memories are ranked by cosine distance.
* Rows with distance <= **0.45** are retained.
* Only the closest row from each source message is retained, preventing one long message from filling the entire result set.
* The top **5** rows are returned.
* If query embedding fails, retrieval falls back to the 5 most recent episodic rows.

Retrieved items enter the system prompt under a section that explicitly treats them as **specific single occasions, not confirmed patterns unless also listed as synthesized memories**.

## Pattern promotion

Function: `synthesize_patterns_from_observations`.

The application groups episodic observations by `(event_type, tag)` and promotes a group when it reaches **3 observations**.

The threshold of **3 observations is an implementation rule for promotion**, not a validated statistical criterion for determining that a behavioral pattern exists.

When a group is promoted, the system creates or updates a versioned synthesized memory. New evidence can be linked to an existing memory, while previous versions are retained in `user_memory_history`.

The LLM does **not** decide whether an observation group qualifies for promotion. The application code applies the promotion threshold. The LLM is used to phrase the synthesized description in a supportive, non-clinical way.

### Automatic trigger

Automatic synthesis runs after analysis when the user's total `behavior_observations` count is a multiple of 3. A manual trigger is also available through `POST /api/v1/memory/synthesize`.

Because the automatic trigger is tied to the user's global observation count rather than to changes in individual `(event_type, tag)` groups, newly eligible evidence may not be synthesized immediately, while some trigger runs may produce no meaningful change.

### Pattern types

* `event_type = behavior` produces `memory_type = pattern`.
* `event_type = emotion` produces `memory_type = emotion_pattern`.
* Only `memory_type = pattern` rows are returned by `GET /analytics/behavior-patterns`, which is what the Progress page currently displays.

### Confidence and evidence

For a synthesized memory, `confidence` summarizes the confidence values produced by the extraction step. For emotion patterns, the corresponding aggregation uses extracted intensity.

This value is **not calibrated** and should not be interpreted as the probability that the synthesized pattern is real. It describes the confidence of the contributing model-generated observations, not the statistical validity of the pattern itself.

The synthesized description reflects the evidence available when the memory is first created and is **not regenerated automatically** when additional evidence is linked.

Evidence links are limited to the 5 most recent rows during an individual synthesis run, but links accumulate across runs. `evidence_count` represents the full number of contributing observations.

## Example

Suppose a user mentions dreading a team meeting, rehearsing a sentence for an hour, and later skipping a group lunch. The extractor may assign observations such as `fear_of_judgment` or `overthinking` to those messages.

When the stored observation count for a given `(event_type, tag)` reaches the promotion threshold of three, the application can create a synthesized pattern memory. The resulting memory contains an LLM-written supportive description, an `evidence_count` of 3, and an aggregated confidence based on the contributing extraction confidences.

The Progress page can then display the synthesized memory as a pattern with an **Add to Journey** action.

The example is illustrative: the current production implementation does not require the three observations to be temporally separated, originate from distinct sessions, or represent independently verified events.

## Why the prompt distinguishes tiers

The chat system prompt treats the memory tiers differently:

* **Synthesized memories** can be described as ongoing tendencies because they represent repeated observations that have passed the application's promotion threshold.
* **Episodic memories** are treated as individual occasions rather than established patterns.
* Past evidence is not intended to be quoted back as proof of a user's behavior.
* The system avoids diagnostic framing.

The purpose of this separation is to reduce over-generalization from isolated observations while keeping the production memory system useful for conversational continuity.

## Limitations

### No recurrence semantics

The current promotion logic counts observations without a time window, distinct-session requirement, or decay. Three observations can therefore qualify for promotion even when they are closely clustered in time or originate from the same long message.

### Extraction quality is unmeasured

There is currently no labeled evaluation set for the extraction layer. Tag accuracy, consistency, and calibration of the underlying 7B model have therefore not been established quantitatively.

### Coarse vocabulary

The current behavior vocabulary contains only seven tags and cannot represent the full range of communication difficulties or behavioral patterns a user might describe.

### Trigger coupling

Automatic synthesis depends on the global `behavior_observations` count rather than directly on newly eligible evidence. This can cause synthesis to be delayed when new evidence becomes eligible, or to run without producing a meaningful update.

### Self-injection surface

User text is provided to the extraction prompt. Extracted evidence sentences are stored and can later be retrieved into that same user's chat context.

Retrieval is scoped by `user_id`, which prevents episodic memories from being retrieved across users. This does not eliminate within-user feedback effects: previously extracted content can influence later extraction, retrieval, and responses.

See [`SAFETY.md`](../SAFETY.md) for the relevant isolation and safety considerations.

### Onboarding memories

Onboarding memories are currently placed in the same prompt section used for established patterns, even though they represent one-time self-reports rather than repeated observations. This is a known limitation tracked separately in [status](status.md).

## What this is not

This production memory system is **not a validated behavioral detector**.

It does not establish that a user has a particular psychological or behavioral trait, and its synthesized patterns should not be interpreted as diagnoses or clinically validated findings.

A separate trained behavioral detector is being studied in the research layer. That research system is intentionally kept separate from this production memory pipeline and is documented in [research](research/README.md).
